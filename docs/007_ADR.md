## ADR-001 — MySQL is authoritative; investigation via transactional outbox
- **Problem:** decision must be durable and investigation must be recoverable without a broker.
- **Decision:** decision row + outbox event committed in one InnoDB transaction; worker polls outbox.
- **Alternatives:** fire-and-forget BackgroundTasks (loses jobs on crash); Kafka now (extra infra, no measured need).
- **Trade-offs:** polling latency + DB load; at-least-once delivery ⇒ worker must be idempotent.
- **Failure:** crash after commit → event still pending → retried. Crash before commit → no decision returned.
- **Scaling:** outbox is the natural Kafka seam (Stage 2) without changing the API contract.

## ADR-002 — Redis is feature state, not the source of truth
- **Problem:** rolling features must be sub-millisecond.
- **Decision:** bucketed counters + Lua atomic updates + TTL + freshness metadata; `noeviction`.
- **Alternatives:** MySQL aggregation per request (too slow at target TPS); in-process memory (not shared across workers).
- **Trade-offs:** ±1 bucket precision; rebuildable but lossy on restart.
- **Failure:** Redis down ⇒ bounded fallback ⇒ partial features ⇒ degraded decision, never zero risk.
- **Scaling:** cluster/shard by customer key; hot-key analysis in Stage 2.

## ADR-003 — In-process parallel orchestrator with deadlines
- **Problem:** three engines, one snapshot, one deadline.
- **Decision:** asyncio gather with per-engine timeout + bounded concurrency; CPU-bound ML/graph in a thread/process pool.
- **Alternatives:** sequential (latency adds up); microservices (network hops + ops cost at MVP).
- **Trade-offs:** GIL contention for CPU work; requires explicit pool sizing.
- **Failure:** slow engine ⇒ `timeout` result ⇒ renormalized weights + degraded flag.
- **Scaling:** engines can be extracted to workers behind the same contract.

## ADR-004 — DuckDB/Parquet strictly off the authorization path
- **Problem:** analytical writes must not add latency or lock contention.
- **Decision:** batched Parquet export from MySQL; DuckDB reads Parquet; single writer process.
- **Alternatives:** write DuckDB per transaction (single-writer contention, wrong tool for OLTP).
- **Trade-offs:** analytics lag (minutes), reconciliation job required.
- **Failure:** export crash ⇒ re-run idempotent batch keyed by decision id/time partition.
- **Scaling:** partition by date; move to object storage later.

## ADR-005 — LLM is advisory, asynchronous, evidence-bound
- **Problem:** explanations are required but must never influence authorization or invent facts.
- **Decision:** post-commit worker; structured JSON; schema + evidence-reference validation; prompt/model versions stored.
- **Alternatives:** synchronous LLM (unacceptable latency/cost/availability coupling); template-only text (weaker narratives).
- **Trade-offs:** eventual consistency; retries and DLQ needed.
- **Failure:** provider outage ⇒ job stays pending with backoff; authorization unaffected; `mock` mode clearly labelled.
- **Scaling:** queue-backed workers, evidence ranking, analyst feedback (Stage 2).

## ADR-006 — Deterministic, versioned decision policy
- **Problem:** identical inputs must yield identical, auditable decisions.
- **Decision:** pure function `(snapshot, engine_results, policy_version) → decision`; config in YAML; version persisted.
- **Alternatives:** logic embedded in code (unauditable); LLM-decided (prohibited).
- **Trade-offs:** calibration work needed to make rule severity / ML probability / graph score comparable.
- **Failure:** unknown policy version ⇒ fail closed to FLAG, log error.
- **Scaling:** enables shadow evaluation and backtesting of candidate policies.
